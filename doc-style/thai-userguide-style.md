# สำนวนภาษาไทยสำหรับ User Guide ส่งลูกค้า

เอกสารนี้สำหรับคนที่กำลังเขียนหรือรีวิว User Guide ภาษาไทย อ่านแล้วเขียนให้ผ่านสายตาลูกค้าได้โดยไม่ต้องแก้สำนวนซ้ำ
ใช้คู่กับ `TEIBTO-USERGUIDE-DOCX.README.md` ใน skill `teibto-doc-standard` ซึ่งคุมเรื่อง layout และ build
ไฟล์นี้คุมเรื่อง **คำ** อย่างเดียว

ที่มา: ถอดคอนเวนชันจากเล่มที่ส่งลูกค้าไปแล้วจริง เทียบกับร่างที่ AI เขียน แล้วสรุปเป็นกฎกลาง (2026-08-08)
กฎเหล่านี้ **ไม่ผูกกับลูกค้าหรือระบบใด** ใช้ซ้ำได้ทุกเล่ม

---

## 1. คำเรียกและระดับภาษา

| กฎ | ควรเขียน | ไม่ควรเขียน |
|---|---|---|
| เรียกผู้อ่านว่า **ผู้ใช้งาน** ตลอดเล่ม | ผู้ใช้งานสามารถตรวจสอบรายการได้จากหน้า Reports | คุณสามารถดูรายการได้จากหน้านี้ |
| ห้ามสลับคำเรียกกลางเล่ม | ใช้ `ผู้ใช้งาน` อย่างเดียว | สลับ `ผู้ใช้` · `คุณ` · `พนักงาน` · ละประธาน |
| ภาษาสุภาพ เป็นกลาง ตรงไปตรงมา | ให้ระบุข้อมูลในช่องที่มีเครื่องหมายดอกจัน (*) กำกับ | กรอกข้อมูลให้ครบ ๆ ก่อนนะ |
| `ต้อง` = ข้อบังคับ · `ควร` = คำแนะนำ · `สามารถ` = สิ่งที่ทำได้ | ผู้ใช้งานต้องระบุ Location ก่อนบันทึก | ผู้ใช้งานสามารถระบุ Location ก่อนบันทึก (ทั้งที่ไม่ระบุแล้วบันทึกไม่ได้) |

## 2. โครงบทและการเปิดบท

- **ชื่อบทบอกงานที่ผู้ใช้งานต้องทำ** ขึ้นต้นด้วย "การ..." และมีเลขลำดับ
  ควรเขียน `1. การสร้างเอกสาร` · `2. การตรวจสอบผลการดำเนินการ` · `3. การยกเลิกเอกสาร`
  ไม่ควรเขียน `หน้านี้ทำอะไรได้บ้าง` · `ใช้ยังไง` · `ทำไมต้องใช้ฟังก์ชันนี้`
- **เปิดบทด้วยสิทธิ์ เงื่อนไข หรือวัตถุประสงค์ ก่อนเข้าขั้นตอนเสมอ**
  `ผู้ที่มีสิทธิ์ในการสร้าง คือ Role : ...`
  `ผู้ใช้งานสามารถยกเลิกเอกสารที่ยังไม่ส่งข้อมูลได้ดังนี้`
- **มีประโยคนำก่อนลำดับขั้นตอน** — `วิธีการ...มีดังนี้` · `ผู้ใช้งานสามารถ...ได้ดังนี้` · `เมื่อ...เรียบร้อยแล้ว ให้...`

## 3. การเขียนขั้นตอน

- เรียงตามจังหวะ **ผู้ใช้ทำ → ระบบตอบ** สลับกันไป

  ```
  1. คลิกปุ่ม Submit
  2. ระบบจะแสดงกล่องยืนยัน
  3. ยืนยันการดำเนินการเพื่อเริ่มสร้างเอกสาร
  ```

  ไม่ควรเขียนรวบเป็นประโยคเดียวว่า "กด Submit แล้วจะมีกล่องขึ้นมา จากนั้นก็กดยืนยันได้เลย"
- **หนึ่งขั้นตอน = หนึ่งการกระทำหลัก** ถ้ามีหลายอย่างให้แตกเป็นข้อย่อย
- ใช้เลขลำดับเมื่อเป็นขั้นตอน อย่ายัดหลายการกระทำไว้ในย่อหน้าเดียว

## 4. คำกริยามาตรฐาน (ใช้ให้คงที่ทั้งเล่ม)

| ใช้คำนี้ | กับสิ่งนี้ |
|---|---|
| `ไปที่` | เส้นทางเมนู |
| `เลือก` | ตัวเลือกหรือรายการ |
| `ระบุ` | การกรอกข้อมูล |
| `คลิก` / `แตะ` | ปุ่มบนหน้าจอ (เลือกตามอุปกรณ์จริง แล้วใช้แบบเดียวทั้งเล่ม) |
| `สแกน` | Barcode หรือ QR Code |
| `ระบบจะแสดง` | ผลลัพธ์บนหน้าจอ |
| `ระบบจะเปิด` | การเปลี่ยนหน้า |
| `ระบบจะดึงข้อมูล` | ข้อมูลที่เติมให้อัตโนมัติ |
| `เลือกช่อง` / `ยกเลิกการเลือกช่อง` | Checkbox |

คำที่ความหมายคลุมเครือ ห้ามใช้: `ยิง` · `ขึ้น` · `ดึงกลับ` · `จัดการให้เอง` · `บล็อก` · `ติ๊ก` · `เอาติ๊กออก`

ตัดคำว่า `ทำการ` หน้าคำกริยา: `คลิกปุ่ม Save` ไม่ใช่ `ทำการคลิกปุ่ม Save`

## 5. เส้นทางเมนู ชื่อปุ่ม ชื่อฟิลด์

- เขียนจากกว้างไปแคบ คั่นด้วย `→` และบอกจุดตั้งต้นเสมอ
  `ที่หน้า Dashboard ไปที่ WMS → Inventory → Fast Transfer`
  ไม่ใช่ `เข้าเมนูนั้นแล้วเลือกอันที่เกี่ยวข้อง`
- **ชื่อปุ่ม ฟิลด์ เมนู ต้องตรงกับหน้าจอจริง** — หน้าจอเขียน `Submit` ก็เขียน `Submit` ห้ามแปลเป็น "ปุ่มส่งข้อมูล"
- **คงชื่อ UI ภาษาอังกฤษไว้ แล้วใช้ภาษาไทยอธิบายหน้าที่**
  `เลือกประเภท Export ในฟิลด์ Truck List` ไม่ใช่ `เลือกส่งออกในช่องรายการรถ`
- ทับศัพท์เมื่อเป็นชื่อระบบหรือคำที่ผู้ใช้เห็นบนจอจริง (`Pallet` · `Lot` · `Location` · `Submit`)
  แต่อย่าให้ทั้งประโยคเป็นอังกฤษ — `User ต้องทำการ check data แล้ว submit transaction` ใช้ไม่ได้
- **อ้างถึงด้วยชื่อ ไม่อ้างด้วยตำแหน่ง** เพราะตำแหน่งเปลี่ยนตามขนาดจอและการจัดหน้าเล่ม
  `คลิกปุ่ม Submit` ไม่ใช่ `คลิกปุ่มด้านล่าง` · `ตามขั้นตอนในหัวข้อ "สร้างใบรับสินค้า"` ไม่ใช่ `ตามขั้นตอนข้างบน`
- **แยกการกระทำกับสถานะ** ชื่อปุ่มใช้กับสิ่งที่ผู้ใช้งานทำ ชื่อสถานะใช้กับผลลัพธ์
  `คลิก Approve แล้วรายการจะมีสถานะ Approved` ไม่ใช่ `รายการถูก Approve แล้ว`

## 6. กรณียกเว้นและข้อผิดพลาด

- ขึ้นต้นด้วย **`กรณีที่...`** เสมอ
  `กรณีที่ไม่พบข้อมูล ระบบจะแสดงข้อความแจ้งเตือน ให้ตรวจสอบป้ายและสแกนอีกครั้ง`
  ไม่ใช่ `ถ้าหาไม่เจอก็ลองยิงใหม่ดู`
- **เงื่อนไขใช้ `และ` หรือ `หรือ` อย่างใดอย่างหนึ่ง** ห้ามเขียน `และ/หรือ`
  `กรณีที่ระบุ Item และ Lot` (ต้องครบทั้งคู่) · `กรณีที่ระบุ Item หรือ Lot` (อย่างใดอย่างหนึ่ง)
- **ข้อความที่ระบบแสดง ให้คัดลอกจากหน้าจอตามจริง** แล้วค่อยอธิบายความหมาย ห้ามสรุปเป็นคำของผู้เขียน
  `ระบบจะแสดงข้อความ "Please enter value(s) for: Location"` ไม่ใช่ `ระบบแจ้งว่า Location ไม่ครบ`
- **แยกผลสำเร็จกับผลไม่สำเร็จให้ครบคู่ พร้อมแนวทางแก้ไข**
  `กรณีที่การส่งข้อมูลสำเร็จ ระบบจะแสดงสถานะ Completed`
  `กรณีที่การส่งข้อมูลไม่สำเร็จ ระบบจะแสดงข้อความใน Field Error Message ให้ตรวจสอบสาเหตุและแก้ไขก่อนส่งอีกครั้ง`
- **ตารางข้อความเตือนต้องมี 3 คอลัมน์เสมอ** ขาดคอลัมน์ไหนก็ใช้ไม่ได้

  | ข้อความที่ระบบแสดง | ความหมาย | แนวทางดำเนินการ |
  |---|---|---|
  | ไม่พบ Bin | ระบบไม่พบ Bin ที่สแกน | ตรวจสอบป้ายและสแกนอีกครั้ง |

## 7. ข้อจำกัด หมายเหตุ ข้อควรระวัง

- **ข้อจำกัดต้องบอกครบ 3 อย่าง: จำนวน · เงื่อนไข · สิ่งที่ต้องทำต่อ**
  `ผู้ใช้งานสามารถเพิ่มรายการได้สูงสุด 24 บรรทัดต่อรอบ เมื่อครบจำนวนแล้ว ให้ Submit ก่อนเริ่มรอบใหม่`
  ไม่ใช่ `ใส่ได้ประมาณ 24 รายการ`
- แยกหน้าที่ให้ชัด: `หมายเหตุ` = ข้อมูลเพิ่มเติม · `ข้อควรระวัง` = สิ่งที่ทำผิดแล้วเกิดผลกระทบ
- **ห้ามใช้ `ฯลฯ` ในรายการที่ผู้ใช้งานต้องตรวจหรือต้องกรอก** ให้เขียนรายการให้ครบ
  `ตรวจสอบ Item, Location และ Quantity` ไม่ใช่ `ตรวจสอบ Item, Location ฯลฯ`

## 8. ภาพประกอบ

- วางภาพ **ทันทีหลังข้อความที่อธิบายภาพนั้น** และอ้างด้วยคำว่า `ดังรูป`
- คำบรรยายภาพบอกเนื้อหาบนจอ เช่น `ภาพหน้าจอการเลือกโหมดการย้าย`
  ห้ามใช้คำบรรยายเชิงกระบวนการภายใน เช่น "ภาพที่ทีม QA ถ่ายจากรอบทดสอบล่าสุด"

## 9. สิ่งที่ห้ามหลุดเข้าไปในฉบับส่งลูกค้า

ชื่อสคริปต์ · ชื่อไฟล์ source code · คำสั่ง build/deploy · HTML comment · ชื่อ branch/repository ·
วิธีถ่ายภาพหน้าจอ · รายละเอียดการทดสอบภายใน · ตัวเลขจากรายงาน QA · ศัพท์ dev ที่ผู้อ่านไม่ต้องใช้

ควรเขียน `แจ้งผู้ดูแลระบบพร้อมข้อความแจ้งเตือนและเลขที่งาน`
ไม่ควรเขียน `ส่ง error log, internal ID และ execution context ให้ Admin`

หากจำเป็นต้องใช้ศัพท์เทคนิคจริง ให้อธิบายความหมายครั้งแรกที่กล่าวถึง

> **ข้อยกเว้นที่ไม่ใช่ข้อผิดพลาด**: notation ของ template เอง (`[btn:Submit]` · `[pill:ครบ]` ·
> `> หมายเหตุ:` · `> ข้อควรระวัง:`) เป็น markup ที่ `build_userguide.py` แปลงเป็นป้ายปุ่ม กล่องสี และรูปป้ายสถานะ
> ให้คงไว้ในไฟล์ .md — จะไม่ปรากฏเป็นข้อความดิบในเล่ม ส่วน HTML comment ไม่ถูกข้าม ต้องตัดออกก่อน build

## 12. เช็คความสม่ำเสมอก่อนส่งมอบ

คำเดียวกันต้องเขียนแบบเดียวตลอดเล่ม — `ผู้ใช้งาน` ไม่สลับกับ `User`/`คุณ` · `Location` ไม่สลับกับ `location` ·
`Pallet` ไม่สลับกับ `pallet` · `คลิก` หรือ `แตะ` เลือกอย่างใดอย่างหนึ่ง · `เอกสาร` หรือ `Record` ต้องมีหลักเกณฑ์ชัดเจน
